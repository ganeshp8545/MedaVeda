# Security and database audit

## Deployment compatibility review — 2026-10-18

The local 53-file migration chain has a previously reported disposable PostgreSQL PASS. The hosted migration table, actual table definitions, Storage policies, buckets and grants are **BLOCKED** without a separate staging project. This review authorizes no hosted push.

| Pending migration | Local dependency and compatibility finding | Hosted result |

| `20261018100000_verified_quiz_attempts.sql` | Uses `quiz_tests.questions`, `subjects`, `profiles.blocked`, `auth.uid()`, `am_i_admin()` (AAL2-aware since `20261001100000`) and `rate_limit_hit()` (`20260924140000`). **Older-client impact:** The Storage restriction deliberately denies direct `notes` bucket writes from older admin panel builds, including upload/replacement/deletion; deploy the matching `upload-note-pdf` function and current admin panel together in staging. Older mobile readers can ignore `notes.description` and the new quiz revision, and the existing `get-note-url` contract is unchanged in source, but an installed old build must be exercised before production rollout. Old `quiz_scores` remain client-supplied and unverified. `quiz_tests.questions` includes the answer key in client-readable data, so even the new backend-calculated score is suitable for practice analytics, not a secure examination result. A secure examination would need server-held answers, controlled question delivery and anti-replay/identity controls.

`upload-note-pdf` checks an authenticated admin and optional AAL2 in code because its gateway `verify_jwt=false`; `get-note-url` has gateway `verify_jwt=true` and checks access through `user_can_access_note`. `sync-play-catalog` and payment workers use their own cron secrets. These are source findings only; deployed JWT configuration, secret presence, RLS and service-to-service behavior are **BLOCKED**. No privileged secret value was displayed or sent.

## Continuation (latest)

A disposable PostgreSQL 17 cluster built the full forward migration chain and ran `supabase/tests/run-all.sh`; its focused `verified_content_checks.sql` reported **0 FAIL, 24 PASS**, including direct Storage write denial, and the existing `medium_db_checks` reported **0 FAIL, 34 PASS** after indexing new foreign keys and wrapping policy auth lookups. The new verified score table denies direct client writes. The note bucket has restrictive insert/update/delete policies, while service-role upload remains possible. `notes.description` defaults to empty for old rows. `get-note-url` and purchase records were not changed. Live migration drift, deployed RLS, actual Storage behavior and malware scanning remain unverified. The initial snapshot below predates these local tests and migrations.

Source evidence: 51 migration files, `supabase/config.toml`, `supabase/functions/get-note-url/index.ts`, `supabase/migrations/20260924120000_critical3_storage_profiles_rls.sql`, `supabase/migrations/20261016090000_free_video_access.sql`. The private `notes` bucket, admin-only Storage policy, note entitlement RPC and role protections are defined in migrations. They were not checked against live migration history or exercised as anonymous/student/admin sessions. `verify_jwt=false` functions have alternate code-level authentication paths (secrets, HMAC, or explicit user auth), but deployment config and rate limits were not penetration-tested.

Open issues are MV-001 (client-supplied scores) and MV-002 (direct Storage upload without trusted content scanning). Remote RLS, cross-user access, migration drift, orphan records, backups and restore are BLOCKED pending an isolated Supabase project and read-only operational evidence. Do not apply migrations to production as part of this audit. A forward-only migration is required for any new database restriction after compatibility testing. Existing notes and purchase records must remain intact.

Safe SQL checks already in `supabase/tests/` can be run against a disposable PostgreSQL instance with `PGHOST`, `PGPORT`, `PGUSER`, and `PGPASSWORD` set. The local cron self-test could not create its scratch database because no reachable PostgreSQL server was available.
