## B. Google Play Console error analysis

**Proven locally:** `app.json` does not list BILLING in its explicit permissions (`mobile-app/app.json:19-22`), but the installed `expo-iap` plugin and Android library do add it at native build time, as cited above. `android.blockedPermissions` does not include BILLING (`mobile-app/app.json:24-30`); the custom queries plugin only adds `<queries>` (`mobile-app/plugins/withAndroidQueries.js:36-61`). There are no checked-in variant manifests or merger rules to remove BILLING. The `production` and `internal-testing` EAS profiles request AABs with Play provider (`mobile-app/eas.json:42-62`). No local release artifact was found. The repository's release gate says a billing AAB has not yet been built/uploaded (`docs/RELEASE_GATES.md:18-22,30-35`).

**What the Console message means:** Google requires `com.android.vending.BILLING` in the **uploaded APK manifest** before enabling one-time products, and a Billing Library build uploaded to a track, including internal testing, enables billing features. See [Play Console product setup](https://support.google.com/googleplay/android-developer/answer/1153481) and [Google's getting-ready guide](https://developer.android.com/google/play/billing/getting-ready). Source configuration alone cannot satisfy the Console.

**Most likely, source-supported explanation:** the selected Play Console app has not yet processed a billing-enabled artifact from this Expo configuration; an older or differently built upload is plausible. A package mismatch is also plausible because repository links target `com.medveda.app` while the configured Android app is `in.medveda.app`. Neither hypothesis is proven without the Console's artifact. The exact root cause of the specific Console state is **NOT VERIFIED**. It would be incorrect to say BILLING is absent from a final release manifest.

**Safest correction to recommend, not perform:** first inspect the artifact attached to the intended Play Console app, record its package/versionCode/versionName/upload time and manifest permissions. If absent or missing BILLING, build the reviewed `internal-testing` profile for `in.medveda.app`, download its AAB, inspect its manifest and resolved Billing Library version, compare versionCode to the selected app's latest upload, then upload that verified AAB to the intended internal track. Do not edit `AndroidManifest.xml` merely because `app.json` omits BILLING. Do not assume a new AAB is safe until the backend/staging gates below are met.

## D. Actual payment flow trace

1. Login uses Supabase auth; payment requests send its bearer session (`mobile-app/src/services/playBillingService.ts:68-86`; `supabase/functions/_shared/supabaseAdmin.ts:24-35`). Product browsing is in `StoreScreen.tsx:53-103,130-182`; `usePurchase.ts:34-39` sends Play builds to `PlayBilling` and Razorpay builds to `OrderSummary`.
2. `PlayBillingScreen.tsx:76-105` fetches a server quote, creates a Play order, queries one SKU, demands INR price equality, then calls `startPlayPurchase`. `create-play-order/index.ts:8-17` authenticates and calls `create_play_order`; SQL checks profile/course/product/ownership and maps price to an active tier (`google_play_ucb.sql:123-142`). No active production tiers are proven.
3. `playBillingService.ts:213-249,251-264` connects through `expo-iap`, installs purchase/error listeners, and calls `requestPurchase({type:'in-app', google:{skus,obfuscatedAccountId,obfuscatedProfileId}})`. The installed package accepts these arguments (`mobile-app/node_modules/expo-iap/src/index.ts:581-623`). `expo-iap` owns the native BillingClient, disconnection and reconnection behavior; those native outcomes cannot be confirmed without an Android build/device. The app uses no explicit one-time offer token, so a complex offer or rent purchase option is outside its proven flow. Google documents option/offer selection in [one-time product offers](https://developer.android.com/google/play/billing/one-time-product-multi-purchase-options-offers).
4. Listener handling (`playBillingService.ts:173-211`) does not grant PENDING or canceled purchases. On PURCHASED it sends the token, product ID and internal order ID to `verify-play-purchase`. An API failure keeps the attempt for restore. `App.tsx:51-67` calls restore on launch, login and resume; `playBillingService.ts:134-170` matches obfuscated account/order hashes or searches that user's existing orders.
5. Server verification (`verify-play-purchase/index.ts:19-48`) checks the authenticated order owner, provider, SKU, Google `purchases.products.get` state, quantity, India region, token/product identity where returned, and obfuscated user/order hashes. The Google API uses the configured package `in.medveda.app` (`googlePlay.ts:29-33,86-95`). The SQL `settle_play_purchase` locks the order, rejects token replay across orders, records payment and purchase, and marks the order paid in one transaction (`google_play_ucb.sql:214-253`). It consumes the reusable price-tier SKU after settlement, which serves as acknowledgement (`verify-play-purchase/index.ts:49-58`). The worker can retry consumption and reverse voided purchases (`play-payment-worker/index.ts:59-137,169-239`). [Google's one-time lifecycle](https://developer.android.com/google/play/billing/lifecycle/one-time) calls for grant then acknowledgement/consumption and refund/void handling.
6. Successful server response triggers the success screen (`PlayBillingScreen.tsx:32-49`); pending triggers a confirming screen (`:50-65`). Purchases are read from server rows with `status='success'` (`mobile-app/src/repositories/purchasesRepository.ts:4-10`); the private note URL endpoint checks `user_can_access_note` before issuing a short-lived URL (`supabase/functions/get-note-url/index.ts:32-62`; `supabase/migrations/20260924150000_free_preview.sql:53-87`). Free previews and admins are intentional alternate access paths. A client success screen itself is not the access control.

**Razorpay path actually present:** the separate `razorpay-distribution` Android profile sets the Razorpay provider (`eas.json:64-72`); the summary then calls `purchaseProduct` and opens an in-app Razorpay WebView (`OrderSummaryScreen.tsx:86-105`; `PaymentCheckoutScreen.tsx:393-430`). The Play profile selects Play and the summary blocks Razorpay. A website Razorpay checkout was not found in the inspected `website/` source. Existing Razorpay entitlements use the shared `purchases` table; the Play app's purchase repository reads successful purchases without filtering payment provider (`purchasesRepository.ts:4-10`), so cross-channel access is supported at the database level. This is not, by itself, a Play policy violation. The live website purchase flow is **NOT VERIFIED**.
