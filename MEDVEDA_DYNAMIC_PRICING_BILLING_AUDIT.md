## 5. Current Product ID Strategy

**Actual strategy: B, shared reusable Play Product IDs per exact price tier.** `products.id` is the content catalog ID; `play_price_tiers.play_sku` is a different identifier keyed by INR selling price; `orders` bind both at creation ([supabase/migrations/20261012100000_google_play_ucb.sql:5](supabase/migrations/20261012100000_google_play_ucb.sql#L5), [same:123](supabase/migrations/20261012100000_google_play_ucb.sql#L123)). The seed script constrains future configured IDs to `notes_<whole INR>` but **does not create any Play product** ([supabase/seed/apply-play-price-tiers.mjs:20](supabase/seed/apply-play-price-tiers.mjs#L20)). This is a shared-tier implementation with a dynamic lookup, not one Play SKU per content item. It supports independent entitlements through order/token binding and server consumption. It does not offer unlimited distinct prices; each new distinct whole-INR price needs a verified Play product/tier.

## 12. Dynamic Pricing Feasibility

**Feasible with backend/catalog work; not currently automatic.** Admin CRUD and server-derived checkout price already exist. Stable content IDs and order snapshots allow preserving prior purchases if content targets remain. New prices cannot be published safely until Play catalog/options are created/verified, regional rules handled, and a read-back gate marks the tier/item ready. Current whole-INR tier format cannot encode arbitrary fractional prices or independent prices without one Play product for each distinct amount. Price updates must account for outstanding orders and multiple countries; current client only accepts INR/India ([mobile-app/src/services/playBillingService.ts:288](mobile-app/src/services/playBillingService.ts#L288), [supabase/functions/verify-play-purchase/index.ts:32](supabase/functions/verify-play-purchase/index.ts#L32)).

## 13. Recommended Architecture

| Approach | Advantages | Limits, cost and required changes |
|---|---|---|
| **A. Reusable consumable price-tier products** | Extends current `play_price_tiers`, client offer query, server token/order binding, consumption and retry system. Few Play products for four approved prices; scales content count when prices repeat. | Every distinct price still needs a Play product. Consumption must complete before user repurchases same SKU. Generic Console listing must accurately describe what is bought. Introduce immutable tier versions/SKUs for price changes, option/region mapping, sync/read-back queue, readiness gate, monitoring and v2 verification. Requires careful pending-order transition. |
| **B. Unique non-consumable Play product per independently purchasable item** | Play product identity directly names entitlement; no consume/rebuy of same item; simpler cross-device Play ownership restoration when catalog stable. | Catalog growth hits documented default product limit, every item/region update costs API operations and review. Product creation/listing/state workflow is larger; existing client/backend/DB must map item ID to Play product, acknowledge non-consumables, migrate prior entitlement logic and keep old SKUs valid. Changing Play price still needs safe pending-order/version handling. |

**Recommendation:** Extend **A** for the current four common price categories, with permanent server entitlements and server-side consumable settlement. Use immutable, versioned Play SKUs for a changed price instead of editing an active SKU while orders can be outstanding. Add a strict draft → syncing → verified → published state; mobile displays the localized Play price and starts checkout only when the server and Play option agree. Do **not** create a Play SKU per chapter by default. Reassess B only if independently priced content grows beyond a manageable tier catalog or Play policy/UX requires content-specific listings. Existing code cannot safely support “unlimited future chapters” literally because Play catalog/product and API limits apply ([Play Console catalog guidance](https://support.google.com/googleplay/android-developer/answer/14590082?hl=en-en), [API quotas](https://developers.google.com/android-publisher/quotas)). Existing purchases stay in `purchases` and retain their original order/price/target snapshots; never rewrite old purchases to new SKUs.

## 19. Proposed Database Migrations

1. **Catalog sync state:** extend `play_price_tiers` or add a narrowly justified version/mapping table for immutable SKU, approved purchase option ID, region price/version, active/published state, sync revision, provider fingerprint and read-back timestamp. Reuse `products`, `orders`, `payments`, `purchases` instead of duplicating them. A separate per-region child table is justified only if multi-region prices are enabled.
2. **Sync job/audit:** add a service-role-only, RLS-protected job table keyed by catalog revision with lease, retry/backoff, terminal error, and idempotency key; add append-only sync audit events. Existing `play_payment_jobs` is for purchase recovery, so do not mix catalog mutations into it.
3. **Publication gate:** transactional Admin RPC validates catalog content, approved price precision, immutable target rules and Play read-back status before `active=true`; no direct client price publication. Preserve old orders and purchases.
4. **Entitlement/content protection:** prevent deletion/reparenting of targets with successful purchases, or retain immutable target records and map replacement content deliberately. Audit existing affected rows before any repair. Restrict video URL columns from broad authenticated SELECT and expose safe metadata separately.
5. **Purchase option and old-tier compatibility:** store option ID and catalog revision on new orders; retain older SKU mappings until outstanding orders/purchases reconcile. Add constraints/indexes through staged backfills; do not rewrite existing purchase tokens.

These are design proposals, **not executable migration instructions**. Validate against actual hosted schema, migration history, old mobile builds, RLS/grants, and Razorpay behavior before approval.
